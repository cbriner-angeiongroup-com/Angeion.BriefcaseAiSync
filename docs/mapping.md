It contains 38 API destination mappings, including labeled conditional narrative groups, and retains the source inventory IDs. `docs/mapping-inventory.csv` is inherited review evidence covering both workbook tabs; it is not the runtime configuration or an assertion that tenant bindings are approved.

The production UDF binding review on November 4, 2026 matched the workbook's questions to active production definitions, including screen names, short names, types and configured choice values. `production-binding-review.json` records 53 verified UDF bindings and their workbook ranges without saved source answers. This replaces 52 placeholder paths and binds the workbook's incident-date question to `Case Incident/GEN-ACCIDENT-DATE`. Duplicate claim-number labels are separated using the workbook's client-insurance and at-fault-insurance sections and production short names. The approved case-header classification mapping remains in place.

One condition remains deliberately unresolved: `REPLACE_WITH_VERIFIED_SCREEN/MotorcycleApplicability`. The user requested that only the helmet answer remain blocked while other vehicle answers are included. The mapper does not read or include that part, and active source validation excludes it. Neither a blank applicability answer nor the general `Automobile Accident` classification is treated as a motorcycle answer. The other four vehicle parts still compose into `vehicleInformation`. The profile remains unapproved and sending-disabled, but this optional exclusion no longer blocks the other enabled mappings.

## Source rules

- All `client*` fields use the explicitly selected primary contact, who may differ from the injured plaintiff. No fallback silently substitutes the plaintiff.
- Primary phone is the configured `Cell` type explicitly marked primary; secondary phone is `Phone 2`. Emergency selection accepts exact label `Emergency` and the explicitly configured production prefix `EC:`. A prefixed label supplies the emergency name after the prefix when comments are absent; supplied comments take precedence. No relationship is inferred. Multiple exact/prefixed emergency candidates are rejected as ambiguous. Other tenants must verify their own labels and prefix. The prefix is deployment-owned and is retained when managed runtime settings are applied.
- Email and address are explicitly primary. Blank values stay absent; duplicated primary selections fail. Address 2 is available as a separate source property and can be joined through `StandardProperties` when approved.
- `clientBillingCountry` passes through the primary address's country name as text (maximum 80 characters). A source name such as `UNITED STATES OF AMERICA` remains unchanged; the profile does not convert it to an ISO country code or change its casing.
- `incidentDate` uses only `Case Incident/GEN-ACCIDENT-DATE`, formatted as `yyyy-MM-dd`. It does not use the case-header incident date or extract a date from narrative text. `Case Incident/GEN-ACCIDENT-SUMMARY` is retained as a labeled incident-summary note. Disagreement between the date answer and narrative requires source review; the mapper does not choose a date from prose.
- Languages, maiden/spouse names, license, texting preference and other enrichment are explicit source fields. Middle name is retained as a labeled entry in `notes`, because the supplied API has no middle-name key; first and last names stay separate. Numeric gender/marital-status IDs require verified dictionaries under `SmartAdvocate:GenderValues` and `MaritalStatusValues`; no numeric enum meanings are guessed. A supplied numeric code without a translation produces `SOURCE_CHOICE_BINDING_REQUIRED`, blocks strict delivery, and remains an explicit field issue in preview. Blank text labels fall back to verified ID translations; an explicitly configured blank translation can represent a tenant-verified absence code. The public contact sample's SSN can be encrypted; actual access/representation must be verified before approval. The app does not invent decryption.
- UDF paths use exact `screenName/udfShortName` from owning case answers, with a root short name when no screen exists. Definition-only rows are skipped, including metadata repeated across answer pages. A response containing only definitions supplies no saved case answers. Other-case answers, missing active flags, inactive mapped UDFs and duplicate paths are rejected.
- `LeadVendorIdUdfPath` binds the workbook's Law Tigers ID/Tiger Lead ID to `leadVendorId`. It must be nonblank, single-line and at most 255 characters. No generated fallback is permitted.
- The old readiness UDF and firm-code gates are removed. Eligibility requires the current main case status to match the configured numeric status in the configured SmartAdvocate tenant; secondary statuses never qualify. The shared profile sets production main status `SE-10.010-SINGLE EVENT-Case Completed` (ID `32409`), verified through `case/status/type` as status type `1` on November 4, 2026. Verify IDs separately for other tenants. Scope and credentials bind that source instance to one destination tenant.
- `caseType` reads the case header's `caseType` through `StandardProperty: CaseType`. The configured translation is `MVA-FB-SE` to BriefCase `Automobile Accident`. Missing or other source types fail validation; no default case type is inferred. This classification mapping does not set the eligibility status or approve the remaining profile.
- The optional deployment-owned `SmartAdvocate:TestTrigger` adds a main-status trigger for exactly one configured internal `SourceCaseId`. It is disabled by default; enabling requires positive `MainStatusId` and `SourceCaseId`. The profile supplies test main status `3886` (`DOCKET ADMIN CASE`) with no selected case. The production trigger continues to qualify normal candidates. Discovery adds the explicit test case without searching the alternate status, and source reload must confirm that case's current main status. Mapping approval, sending, identity and upload rules still apply.

The user corrected the production gender choices on November 6, 2026: gender `0` = `Female` and gender `1` = `Male`, reversing the earlier November 4 confirmation. Profile version `farrar-ball-smartadvocate-production-unapproved-8` explicitly configures these translations. Marital status `1` = `Married` remains as confirmed on November 4. Other numeric choices remain blocked until verified. Middle name in a labeled note was also explicitly approved for this mapping. Frozen retries retain their original request and version; existing BriefCase intakes require manual correction rather than another create.

## Translation and validation

Mappings allow a standard property, enriched source field, exact UDF, or explicitly configured precedence between standard and UDF. `RejectConflict` is the default. Narratives join labeled answers with actual newlines and evaluate configured parent conditions. Missing versus explicit No are distinct. Every choice must have a translation when a translation dictionary is present; an `Other` incident is not silently changed into an automobile case.

Only an optional scalar narrative part can be explicitly disabled, and it must retain a label and nonblank reason. Required parts and whole destinations cannot be disabled. Disabled parts and their conditions are excluded before source lookup; they are never converted to No or sent under another API key. Preview shows each disabled part as a separate blocked row with no outbound value, while the parent field counts only enabled parts. Errors in any enabled part still block its parent. Frozen retries continue to display and send their original request and mapping version; a newer optional exclusion never edits an already frozen request.

The API requires first/last name, case type, Tiger ID, and email or primary phone. Mobile alone does not satisfy contactability. Checkbox values are Yes/No strings; dates emit `yyyy-MM-dd`. Picklists, case types/subtypes, phone/SSN formats, state codes and aggregate text lengths are validated before sending. Unsupported destinations are rejected. Untracked subtype, SOL, sovereign-immunity and records-only fields remain omitted in the workbook profile. The vendor supplies its documented general subtype default.

## Additional people

The workbook's second tab specifies `description` with exact labels and blank-line-separated person blocks. The main sheet also mentions `clientGuardianPerson`; the PDF lists that key but not `description`. These are distinct contracts. The November 6, 2026 correction removes the direct `Case Incident/PLAINTIFF-DETAILS` mapping to `clientGuardianPerson`: this is free text and can contain an incident narrative, not a verified guardian name. Profile version `farrar-ball-smartadvocate-production-unapproved-7` preserves it under the label `Plaintiff details` in `notes`. The incident summary remains separately labeled, even when the source repeats the same text in both answers. No text matching or inferred guardian extraction is performed. `clientGuardianPerson` is omitted until a reliable guardian-specific binding is verified.

Generated `description` blocks require both `DescriptionEnabled=true` and `DescriptionContractVerified=true`. The firm comment supplied by the user on November 6, 2026 identifies the absent `description` as the reason additional-person details were missing and accepts omission for an adult single-person lead. This confirms the intended field despite its omission from the older API PDF. Profile version `farrar-ball-smartadvocate-production-unapproved-9` enables both flags and follows the workbook's complete narrative format, including the main contact even when they are the only person. The whole profile remains unapproved and sending-disabled. This confirmation establishes the intended field, not a live write or updated API length guarantee; the existing conservative 32768-character validation limit remains in place pending acceptance.

Production source metadata verifies role ID `26411`, `(P)-Plaintiff`, as `Client`. This is the only production role currently configured in `SmartAdvocate:PersonRoles`. Guardian, representative and other roles must receive their own verified bindings before cases containing them can send; no role is inferred from primary-contact status or names. Unknown or conflicting roles and missing person names block delivery. Preview retains available contact fields and shows a `description` field issue rather than silently omitting a person. Removed case-person rows are excluded, and repeated rows for the same contact and role produce one block.

A checked-in mapping correction does not change managed SQL settings or an existing BriefCase record. Promote the revised mapping and deployment-owned role dictionary through the approved configuration workflow. Already frozen retries retain the original request and mapping version, and acknowledged intakes with changed desired values require manual correction through `UpdateRequired`.

Every included source role must map through `SmartAdvocate:PersonRoles` to `Client`, `Guardian`, `Representative`, or `Other`. Core composes one block per contact using exact workbook labels and real newlines, with a blank line between blocks. First/last names are required; each person's own explicitly primary phone/email, date of birth and known deceased status are included when available. Missing death dates do not become `Deceased: No`. Minor status and family relationships remain omitted because their reliable source bindings are not specified. The primary contact can be a guardian or representative while a different person is the injured client; the normal `client*` fields still belong to the selected primary contact.

## Document type mapping

The source document's `docType` maps to required BriefCase `documentType`, as confirmed by the user on November 9, 2026. `DocumentTypeMappings` is separate from intake field mappings and editable in Configuration. Initially each of the six supported BriefCase labels maps from the identical SA name. Operators can change source names without changing the vendor's accepted labels. Matching is exact, with no automatic default or inference from a filename, extension, category, tag or subcategory. The existing OnTask / Submitted File eligibility rule and configured classification IDs continue to select documents; `docType` supplies the type of each selected document.

Each new upload freezes the mapped type and complete init request before HTTP. Retry uses the stored request, even after mappings or source metadata change. Existing delivered content is not re-uploaded solely because its type mapping changed; correcting a delivered classification requires vendor-side review. Older pending sessions without a frozen type require explicit operator review before any fresh initialization. Existing initialized sessions may resume/complete; expired sessions without a frozen type cannot automatically initialize a replacement.
